# ТЗ — власна СРМ (заміна KeyCRM)

> Статус: **чернетка для обговорення**. Нічого з цього ще не кодиться — документ фіксує домовлене,
> модель даних і повну архітектуру сторінок, щоб на його основі можна було виконати роботу (людині
> чи AI-виконавцю) і наперед точно знати результат.
> Фоновий проєкт — KeyCRM продовжує працювати паралельно, дедлайну «замінити зараз же» немає.

## 1. Навіщо

Зараз обидві воронки (`goverla_shop`, `covercar_ua`) працюють поверх KeyCRM: каталог товарів,
кастомні поля, створення замовлень. KeyCRM — універсальна CRM «для всього» (ліди, кілька
типів воронок продажів, дзвінки, звіти тощо), а нам реально потрібна вузька підмножина
функціоналу — плюс кілька речей, яких у KeyCRM взагалі немає (розбивка витрат по товару,
щоденні рекламні витрати, зв'язок реклами з конкретним товаром, аналітика по воронці продажів).

**Бачення продукту:** це СРМ для будь-кого, хто продає товари через інтернет (Instagram,
соцмережі) — і продаватиметься як **єдиний пакет разом з нашою AI-воронкою продажів**, не
окремо. Тобто інтерфейс і функціонал мають бути достатньо загальними для чужого магазину,
а не хардкодити специфіку goverla/covercar.

**Принцип, з якого виходимо:** вписуємо рівно той функціонал, який реально потрібен для
роботи воронки + явно запрошені нижче фічі (реклама/витрати/ТТН/аналітика/повернення) — і
більше нічого зайвого з типової CRM (ліди, дзвінки, універсальний inbox).

## 2. Архітектурні рішення

| Питання | Рішення |
|---|---|
| Де жити | Окремий мікросервіс з нуля — своя БД, свій API/MCP. Не таблиці всередині platform. |
| Мультитенантність | Одразу, з першого дня — кілька магазинів (tenants) на одному сервісі, дані ізольовані по tenant. |
| Веб-UI | Потрібен — власник керує каталогом і замовленнями вручну через веб-інтерфейс. |
| Мігрувати каталог KeyCRM | Так, повністю — товари, кастомні поля, ціни один раз переносяться скриптом-міграцією. |
| Облік залишків/складу | Немає — товар завжди «під замовлення». |
| Картка клієнта (buyer) | Так — з історією замовлень, дедуп за телефоном. |
| Статуси замовлень | Гнучкі стадії (не копія KeyCRM pipeline-для-всього) — Клієнт + Замовлення, а стадії налаштовуються через MCP. |
| Темп | Фоновий проєкт, паралельно з живою KeyCRM. |
| Автентифікація | **SSO** — той самий вхід, що й в усі інші системи FINEKO (єдиний обліковий запис, дивись панель `/admin` — каталог продуктів × користувачів). |
| Домен | **`crm.fineko.space`** |
| Постачальник (`SUPPLIER_MAP`) | **Переноситься в СРМ** — сутність `Supplier` (§4.4) + `Product.supplierId`, замість json-мапи в funnelKey воронки. |
| `description` товару | **Лишається окремим полем** — `presentationText` (§4.2), не генерується на льоту з інших полів. |
| MCP-стиль | **Той самий стиль**, що вже є в `platform` MCP (`list_/get_/create_/update_` префікси, `Authorization: Bearer`). |
| UI-дизайн | Структура й підхід — схожі на адмінку FINEKO Flows (той самий каркас: бокове меню, картки, таблиці), **темна тема**. Кольорова гама — **своя**, відмінна від Flows, щоб кожна система на FINEKO візуально впізнавалась окремо. |
| Ролі користувачів | **Через SSO** — не окрема сутність усередині СРМ; хто з якими правами заходить у tenant, керується так само, як і в інших системах FINEKO (`/admin`-панель доступів). |
| Файлове сховище | **Локально на VPS** — є вільне місце, окремий S3-сумісний сервіс не потрібен. |
| Облік повернень/обмінів | **Так, окрема сутність** — `Return` (§4.11), інакше маржа й конверсія в аналітиці будуть завищені. |
| Лог доставки інтеграцій в UI | **Не потрібен** — досить серверних логів, окрему вкладку/сторінку для цього не робимо. |
| Атрибуція реклами | **First-touch і last-touch одночасно** — обидва поля на замовленні (§4.8), не тільки перший дотик. |
| Формула витрат на менеджера | **Два прості поля замість вільної формули**: фіксована сума за товар + відсоток від суми продажу за товар (§4.10). |
| Хто опитує Нову Пошту | **Через FINEKO Flows** — окрема автоматизована воронка (крон-flow) опитує API Нової Пошти й записує `ttnStatus` у СРМ через її ж write-API. Сама СРМ зовнішній опитувальник не тримає. |
| Рекламні витрати/кліки ↔ Zernio | **Zernio цього ще не вміє — робимо самі, теж через FINEKO Flows.** Окрема воронка/автоматизація підключається до рекламних кабінетів (Meta Ads API), щодня забирає витрати й кліки та пише їх у СРМ через write-API (§5). |
| `AdClick` для органічних звернень | Підтверджено — сесії без реклами просто виключаються з розрахунків §6.2/§6.5, `firstTouchAdId`/`lastTouchAdId` лишаються порожніми. |

## 3. Структура меню (за скріншотами-побажаннями)

**Каталог**
- Товари
- Категорії
- Постачальники

**Продажі**
- Воронки *(= Pipeline/Stage, налаштовується через MCP)*
- Замовлення
- Покупці
- Повернення/обміни *(нове — §4.11)*

**Реклама та аналітика**
- Дашборд аналітики
- Рекламні витрати

**Фінанси**
- Журнал платежів
- Витрати по товару

**Налаштування** *(gear-іконка)*
- Загальні (назва магазину, API-ключ)
- Інтеграції (Zernio-кабінети, Нова Пошта, webhook воронки)

Прибрано повністю: список товарів → без «Залишки»/«Резервування»/«Комплектуючі»; продажі →
без «Списки замовлень»/«Історія дзвінків»; з бокового меню — вбудований чат/inbox (соцмережевий
чат обробляє AI-воронка, дублюючий інбокс лише плутатиме).

## 4. Модель даних

### 4.1 Tenant (магазин-власник)
**Tenant = окремий магазин-клієнт СРМ** (напр. goverla_shop і covercar_ua — це два різні
tenant, навіть якщо власник той самий; коли продукт продамо іншому власнику IG-магазину,
він отримає свій окремий tenant). Ізоляція мультитенантності — все нижче прив'язане до
`tenant_id`, дані одного tenant не видно іншому.

| Поле | Опис |
|---|---|
| `id` | UUID |
| `name` | назва магазину (для UI) |
| `apiKey` | токен для доступу воронки/MCP до даних саме цього tenant (секрет живе у funnelKey воронки, не в `.env`) |
| `ssoOrgId` | зв'язок з обліковим записом у SSO-панелі FINEKO |

### 4.2 Product (товар)

| Поле | Було в KeyCRM | Зміни за побажаннями |
|---|---|---|
| `id`, `name`, `sku`, `price`, `minPrice`, `categoryId` | без змін | — |
| `presentationText` | `description` | Перейменовано з «Опис товару» на «Презентація для клієнта» — готовий текст, який бот показує клієнту verbatim |
| `adMatchTokens` | `custom_fields[CT_1001]` | без змін — токени для матчингу за рекламою/артикулом |
| `companionProductIds[]` | `custom_fields[CT_1003]` (одне посилання) | Багато-вибір (dropdown, мультивибір товарів) замість одного значення |
| `setComponents[]` | `custom_fields[CT_1005]` (рядок-токен) | Багато-вибір (dropdown, мультивибір товарів + кількість) — `{productId, qty}[]` |
| `supplierId` | `custom_fields[supplier]` / `SUPPLIER_MAP` | FK на сутність `Supplier` (§4.4) |
| `supplierArticle` | `custom_fields[CT_1006]` | без змін |
| `sizeChartImage` | посилання на зображення | Файл, завантажений у нашу систему (локальне сховище) |
| ~~`sizes[]`~~ | окремий блок «Розміри» на картці | Прибрано повністю — розміри живуть у варіантах (`Offer.properties`) |

### 4.3 Offer (варіант товару — колір/розмір)

| Поле | Опис |
|---|---|
| `id`, `productId`, `sku`, `price` | без змін |
| `properties[]` | `{name, value}` — розмір/колір тощо |
| `images[]` | до 10 фото на кожен колірний варіант (Instagram дозволяє альбом до 10 фото в одному повідомленні) |

### 4.4 Supplier (постачальник)

| Поле | Опис |
|---|---|
| `id`, `tenantId` | — |
| `name` | назва постачальника |
| `mechanism` | як оформлюється замовлення постачальнику (ручне / EasyDrop / BrewDrop / інше) |
| `contactInfo` | контакти для ручного оформлення |

### 4.5 Category (категорія)

| Поле | Опис |
|---|---|
| `id`, `tenantId`, `name` | — |
| `description` | опис категорії |
| `aiInstructions` | що саме бот має дізнатись у клієнта для товарів цієї категорії (зріст/вага для одягу, розмір ноги для взуття тощо) — заміняє хардкод правил під категорію в промпті `n_size` |

### 4.6 Buyer (клієнт)

| Поле | Опис |
|---|---|
| `id`, `tenantId`, `fullName`, `phone` (унікальний дедуп-ключ), `igUsername` | — |

### 4.7 Pipeline / Stage (стадії замовлення)

`Pipeline{id, tenantId, name}` + `Stage{id, pipelineId, name, order}`, редагується через MCP
або зі сторінки «Воронки», без хардкоду в сервісі.

### 4.8 Order (замовлення)

| Поле | Опис |
|---|---|
| `id`, `tenantId`, `buyerId`, `stageId`, `sourceName`, `managerComment`, `shipping{}` | без змін |
| `items[]` | `{productId, offerId?, name, price, quantity, properties[], isUpsell}` — `isUpsell` позначає допродаж, не основний товар |
| `ttn[]` | номер(и) ТТН Нової Пошти (масив), заповнюється з воронки |
| `ttnStatus` | статус доставки, автосинк через Нову Пошту (§6.4) |
| `firstTouchAdId` / `firstTouchAt` | реклама/час першого дотику клієнта — атрибуція |
| `lastTouchAdId` / `lastTouchAt` | реклама/час останнього дотику перед покупкою (якщо клієнт клікав кілька реклам) |

### 4.9 Ad / AdSpendDaily / AdClick

| Сутність | Поле | Опис |
|---|---|---|
| `Ad` | `id`, `tenantId`, `externalId`, `name`, `productId` | прив'язка реклами до конкретного товару |
| `AdSpendDaily` | `id`, `adId`, `date`, `amount`, `currency` | щоденна витрата, тягнеться автоматично через Zernio |
| `AdClick` | `id`, `adId`, `sessionId`, `timestamp` | подія «клік»: перше повідомлення нової сесії воронки з `entryAd` = цей `adId` |

### 4.10 ProductExpense (витрати по товару)

| Поле | Опис |
|---|---|
| `id`, `productId`, `tenantId` | — |
| `cogs` | собівартість товару (ручне поле) |
| `managerCostFixed` | витрати на менеджера — **фіксована сума за товар** |
| `managerCostPercent` | витрати на менеджера — **відсоток від суми продажу за товар** |
| `adSpend` | автоматично — сума `AdSpendDaily` по рекламах цього товару за період |

Маржа рахується як: `ціна_продажу − cogs − adSpend − managerCostFixed − (ціна_продажу × managerCostPercent / 100)`.

### 4.11 Return (повернення/обмін) — нова сутність

| Поле | Опис |
|---|---|
| `id`, `tenantId`, `orderId` | зв'язок із замовленням |
| `type` | `return` (повернення) або `exchange` (обмін) |
| `reason` | причина (текст) |
| `status` | нове / підтверджено / завершено |
| `createdAt` | дата звернення |

Використовується в аналітиці (§6.3/§6.2), щоб повернені замовлення не рахувались як
«чистий» продаж/дохід.

## 5. API / MCP — операції, потрібні воронці

Рівно те, що сьогодні викликає `n_lookup-code.js` і `n_crm_order`-нода: список каталогу (з
варіантами/фото), пошук за sku, пошук клієнта за телефоном, створення замовлення, зміна
стадії — плюс: запис ТТН, читання `ttnStatus`, запис `AdClick`, запис
`firstTouchAdId/At`+`lastTouchAdId/At`, запис `Return`. MCP — для налаштування (товари,
категорії, постачальники, стадії pipeline, підключення рекламних кабінетів).

**Додатково — write-ендпоїнти для автоматизацій на FINEKO Flows** (не для основної
воронки продажів, а для окремих службових flow-автоматизацій, див. §2): `PATCH
/orders/:id/ttn-status` (пише статус, отриманий крон-flow'ом опитування Нової Пошти) і
`POST /ad-spend-daily` + `POST /ad-clicks` (пише щоденні витрати/кліки, отримані окремою
crontab-воронкою, яка ходить у Meta Ads API). Обидва — з тим самим Bearer tenant `apiKey`,
що й основна воронка.

## 6. Аналітика

Окремий дашборд, що відповідає рівно на 5 запитаних питань — без зайвого «BI про все»:

1. **Який товар найбільше купують** — топ товарів за кількістю/сумою продажів
   (`Order.items[]`, за період, мінус позиції зі зв'язаним `Return`), з фільтром «без
   допродажів» (`isUpsell=false`) і «включно з допродажами».
2. **На яку рекламу найбільше клікають / з якої найбільше купують** — по кожному `Ad`:
   кількість `AdClick` проти кількості замовлень з `Order.firstTouchAdId` **або**
   `lastTouchAdId = adId` (два окремих зрізи — «хто привів» і «хто дотиснув») → CTR і
   конверсія поруч, мінус повернені замовлення.
3. **Який товар приносить найбільше маржі/чистого прибутку** — дохід з `Order.items[]`
   (мінус повернені) мінус `ProductExpense` за період, топ за чистим прибутком.
4. **З якого товару найбільше допродажів / який товар найкраще допродається** — (а)
   «купуючи товар X, найчастіше додають Y»; (б) топ товарів за тим, як часто САМЕ ЇХ
   беруть як допродаж і приймають (upsell acceptance rate).
5. **Середній час від кліку до покупки** — різниця `Order.createdAt − Order.firstTouchAt`,
   усереднена по товару/рекламі/загалом.

Усі 5 звітів мають фільтр за періодом (день/тиждень/місяць/довільний діапазон) і, де
доречно, за конкретним товаром/рекламою.

## 7. Відкриті питання

Лишилось одне некритичне питання — решту закрито (див. §2):

1. **Назва продукту** — робоча назва для документа/репо (не критично зараз, можна лишити
   робочу назву на кшталт «FINEKO CRM» і повернутись до цього перед публічним запуском).

## 8. Свідомо НЕ включаємо

- Облік залишків/складу.
- Ліди / інші типи воронок (маркетинг-CRM функціонал KeyCRM для лідогенерації) — тільки
  клієнт + замовлення.
- Дзвінки/історія дзвінків.
- Вбудований чат/inbox для спілкування з клієнтом — це робить AI-воронка.
- Окрема UI-сторінка/лог доставки інтеграцій — досить серверних логів.
- Загальне BI «про все» — тільки 5 конкретних звітів із §6.
- Інтеграції з маркетплейсами (Rozetka/Prom тощо).
- Email/SMS-розсилки.
- Публічний self-serve онбординг для інших власників магазинів, тарифікація, білінг — Фаза 2.

## 9. Архітектура сторінок (детальна специфікація UI)

Загальний каркас — як у адмінці FINEKO Flows: ліве вертикальне меню з іконками (розділи
§3), темна тема, основний контент — таблиця/картка праворуч, форми створення/редагування —
в бічній панелі (drawer) або модалці, без переходу на окрему сторінку. Стек і точний
компонентний фреймворк — окреме архітектурне рішення (§7), тут описано лише що саме має
бути на екрані.

Кожна сторінка нижче описана за одним шаблоном: **Призначення → Макет → Поля/Колонки →
Дії → Порожній стан → Дані (яка модель/API годує сторінку)**.

---

### 9.1 Вхід (SSO)

- **Призначення:** автентифікація через єдиний SSO FINEKO, без власної форми логіну.
- **Макет:** екран-заглушка з логотипом і кнопкою «Увійти через FINEKO ID» → редірект на
  SSO, назад — з токеном сесії. Якщо в SSO-акаунта немає доступу до жодного tenant —
  екран «У вас поки немає доступу до жодного магазину, зверніться до адміністратора».
- **Дані:** `tenantId`, права доступу — з SSO/`/admin`-панелі.

---

### 9.2 Товари — список

- **Призначення:** огляд і пошук усього каталогу товару.
- **Макет:** таблиця на всю ширину, зверху — пошук за назвою/sku, фільтр за категорією,
  фільтр за постачальником, кнопка «+ Товар» справа зверху.
- **Колонки:** фото (мініатюра `thumbnailUrl`), назва, sku, категорія, ціна, кількість
  варіантів (offers), постачальник, дата оновлення.
- **Дії на рядок:** редагувати (відкриває 9.3), дублювати, видалити (з підтвердженням,
  тільки якщо товар не задіяний у жодному активному замовленні).
- **Порожній стан:** «Товарів ще немає» + кнопка «+ Товар» і посилання «Або імпортувати з
  KeyCRM» (запускає міграцію §10).
- **Дані:** `Product` (список, пагінація/безкінечний скрол), `Category.name` для фільтра,
  `Supplier.name` для фільтра.

### 9.3 Товар — картка/форма (створення й редагування — одна форма)

- **Макет:** дві колонки. Ліва — основні поля, права — фото/варіанти.
- **Ліва колонка, поля:**
  - Назва (текст, обов'язкове)
  - Артикул `sku` (текст, обов'язкове, унікальне в межах tenant)
  - Ціна / Мін. ціна (число)
  - Категорія (select із `Category`, обов'язкове)
  - **Презентація для клієнта** (`presentationText`) — багаторядковий текст, це те, що бот
    надішле клієнту verbatim; під полем — підказка «Пишіть так, як має прозвучати для
    клієнта, а не сухий CRM-опис».
  - Токени для матчингу за рекламою/артикулом (`adMatchTokens`) — текстове поле з тегами
    (додав слово/код → enter → чіп).
  - **Допродажі** (`companionProductIds[]`) — dropdown з мультивибором, пошук по назві
    товару, показує вибрані як чіпи.
  - **Склад набору** (`setComponents[]`) — dropdown з мультивибором товарів + поле
    «кількість» біля кожного вибраного (для наборів на кшталт «кофта + джинси + футболка»).
  - **Постачальник** (`supplierId`) — dropdown (select) із сутності `Supplier`, з посиланням
    «+ додати постачальника» одразу тут (відкриває міні-форму 9.6 у модалці, без переходу).
  - Артикул у постачальника (`supplierArticle`) — текст.
- **Права колонка:**
  - **Розмірна сітка** — завантаження зображення (drag&drop або вибір файлу), прев'ю,
    кнопка «замінити»/«видалити».
  - **Варіанти (Offers)** — таблиця/список карток: колір, розмір, sku, ціна, і для КОЖНОГО
    кольору — **галерея до 10 фото** (drag&drop, порядок можна міняти перетягуванням,
    перше фото = головне). Кнопка «+ Варіант».
  - Блок «Розміри» — **відсутній повністю** (розміри — лише властивість варіанта вище).
- **Дії:** «Зберегти», «Скасувати», (при редагуванні) «Видалити товар».
- **Валідація:** назва + sku обов'язкові; sku унікальний; хоча б один варіант (Offer) для
  публікації товару (можна зберегти чернетку без варіантів).
- **Дані:** `Product`, `Offer[]`, `Category[]` (для select), `Supplier[]` (для select),
  `Product[]` (для мультивибору допродажів/набору).

### 9.4 Категорії — список + форма

- **Список:** таблиця — назва, кількість товарів у категорії, дії (редагувати/видалити,
  видалення заблоковане якщо є товари в категорії — спершу перенести товари).
- **Форма (drawer):**
  - Назва (текст, обов'язкове)
  - Опис (`description`) — багаторядковий текст
  - **Інформація для ШІ** (`aiInstructions`) — багаторядковий текст з підказкою «Що бот
    має дізнатись у клієнта для товарів цієї категорії (напр. зріст і вага для одягу,
    розмір ноги для взуття)».
- **Дані:** `Category`.

### 9.5 Постачальники — список + форма

- **Список:** таблиця — назва, механізм оформлення, кількість прив'язаних товарів, дії.
- **Форма (drawer/модалка):** назва, механізм (select: ручне / EasyDrop / BrewDrop /
  інше), контактна інформація (текст).
- **Дані:** `Supplier`.

---

### 9.6 Воронки (Pipeline / Stages)

- **Призначення:** налаштувати стадії, якими проходить замовлення (заміна KeyCRM
  pipeline_id/status_id, але просто).
- **Макет:** список стадій однієї воронки як картки в ряд (kanban-заголовки), кожну можна
  перейменувати, перетягнути для зміни порядку, видалити (якщо немає замовлень на цій
  стадії) або додати нову стадію («+»). Якщо кілька Pipeline на tenant — перемикач зверху.
- **Дані:** `Pipeline`, `Stage[]`. Ця ж сторінка — UI-еквівалент MCP-налаштування стадій.

### 9.7 Замовлення — список (Kanban + таблиця)

- **Призначення:** основний робочий екран менеджера.
- **Макет:** перемикач вигляду «Дошка» / «Таблиця» зверху праворуч.
  - **Дошка (за замовчуванням):** колонки = стадії з 9.6, картки замовлень усередині
    (ім'я покупця, сума, товар(и) одним рядком, бейдж `ttnStatus` якщо є ТТН), drag&drop
    картки між колонками = зміна стадії.
  - **Таблиця:** колонки — № замовлення, дата, покупець, товар(и), сума, стадія (dropdown
    прямо в рядку), ТТН + статус доставки, джерело (`firstTouchAdId`/органіка).
- **Фільтри зверху:** за стадією, за періодом, за товаром, пошук за покупцем/телефоном/ТТН.
- **Дії:** «+ Замовлення» (ручне створення, рідкісний кейс — основний потік замовлень
  приходить з воронки), клік на рядок/картку → 9.8.
- **Порожній стан:** «Замовлень ще немає» (з поясненням, що вони приходять автоматично
  з воронки після оформлення клієнтом).
- **Дані:** `Order` (+ `Stage.name`, `Buyer.fullName`, `Product.name` для відображення).

### 9.8 Замовлення — деталі (drawer/модалка з рядка списку)

- **Секції:**
  - Покупець: ім'я, телефон (клікабельний → 9.10), посилання на Instagram.
  - Товари: список позицій (`items[]`) з міткою «Допродаж» біля тих, де `isUpsell=true`.
  - Доставка: місто, відділення НП, ТТН (може бути кілька, кожен — окремий рядок),
    поточний `ttnStatus` (авто-оновлюваний бейдж), кнопка «Оновити зараз» (ручний
    форс-запит до API Нової Пошти).
  - Оплата/коментар менеджера: вільний текст `managerComment`.
  - Атрибуція: перша реклама (`firstTouchAdId`) і остання перед покупкою (`lastTouchAdId`),
    якщо були — з назвою оголошення.
  - Стадія: dropdown зі стадіями поточного pipeline.
  - Кнопка «Оформити повернення/обмін» → відкриває форму 9.11, прив'язану до цього
    замовлення.
- **Дані:** `Order` повністю, `Buyer`, `Ad` (для назв реклам), `Return[]` якщо є.

### 9.9 Покупці — список

- **Макет:** таблиця — ім'я, телефон, Instagram, кількість замовлень, сума всіх покупок,
  дата останнього замовлення. Пошук за ім'ям/телефоном.
- **Дії:** клік на рядок → 9.10.
- **Дані:** `Buyer` + агреговані `Order`.

### 9.10 Покупець — картка

- **Секції:** контактні дані (ім'я, телефон, Instagram), історія замовлень (таблиця, клік
  на рядок → 9.8), загальна сума покупок, кількість повернень.
- **Дані:** `Buyer`, `Order[]`, `Return[]`.

### 9.11 Повернення/обміни — список + форма

- **Список:** таблиця — дата, замовлення (посилання на 9.8), покупець, тип
  (повернення/обмін), причина, статус.
- **Форма:** прив'язка до замовлення (якщо відкрито не з 9.8 — пошук замовлення за
  номером/покупцем), тип (radio: повернення/обмін), причина (текст), статус (select:
  нове/підтверджено/завершено).
- **Дані:** `Return`, `Order` (для пошуку/відображення).

---

### 9.12 Дашборд аналітики

- **Макет:** зверху — спільний фільтр періоду (день/тиждень/місяць/довільний діапазон) і
  опційний фільтр за товаром/рекламою, що впливає на всі блоки нижче. П'ять блоків-карток
  на сітці 2 колонки:
  1. **Топ товарів за продажами** — горизонтальна стовпчикова діаграма + таблиця
     (перемикач «без допродажів» / «з допродажами»).
  2. **Реклама: кліки → покупки** — таблиця по кожній рекламі: кліки (`AdClick`),
     покупки (first-touch), покупки (last-touch), конверсія %, витрата (з `AdSpendDaily`),
     ціна за покупку.
  3. **Маржа по товару** — таблиця, сортована за чистим прибутком: дохід, витрати
     (`ProductExpense`), маржа, маржа у %.
  4. **Допродажі** — дві міні-таблиці поруч: «Найчастіше докуповують з X → Y» і «Найкраще
     допродається (acceptance rate)».
  5. **Час клік → покупка** — число (середнє, медіана) загалом + розбивка по товару/рекламі
     як таблиця, сортована за швидкістю конверсії.
- **Дані:** агреговані запити з `Order`, `AdClick`, `AdSpendDaily`, `ProductExpense`,
  `Return` (виключення повернених з розрахунків прибутку/конверсії).

### 9.13 Рекламні витрати

- **Макет:** таблиця дата × кабінет/оголошення × товар × сума, з фільтром за періодом і
  товаром. Рядки, де оголошення ще НЕ прив'язане до товару, підсвічені й мають inline
  dropdown «Прив'язати до товару» прямо в рядку (без окремої сторінки).
- **Джерело даних:** автоматичне щоденне підтягування через Zernio-конектор (крон), ручне
  редагування суми не передбачене (лише прив'язка товару).
- **Дані:** `AdSpendDaily`, `Ad` (прив'язка до `Product`).

---

### 9.14 Журнал платежів

- **Макет:** таблиця — дата, замовлення (посилання на 9.8), сума, метод оплати, статус
  (той самий потік, що зараз звіряється через Monobank/ibanoplata на боці воронки — тут
  лише відображення журналу, без зміни логіки звірки).
- **Дані:** платежі, пов'язані з `Order`.

### 9.15 Витрати по товару

- **Макет:** таблиця товарів з редагованими прямо в рядку (inline edit) полями:
  собівартість (`cogs`), витрати на менеджера — **фіксована сума** (`managerCostFixed`) і
  **% від суми продажу** (`managerCostPercent`) — два окремих поля поруч. Автоматична
  колонка `adSpend` (тільки читання, з §9.13). Колонка «Маржа» — результат обчислення за
  формулою з §4.10, показана і в грошах, і у %.
- **Дії:** збереження зміни поля одразу (autosave).
- **Сповіщення:** якщо для товару за день/тиждень маржа стає від'ємною (витрати >
  дохід) — автоматичний Telegram-алерт власнику (той самий `notifyTg`-патерн, що вже
  використовується в самій воронці), без потреби відкривати цю сторінку вручну.
- **Дані:** `ProductExpense`, `AdSpendDaily` (агреговано), `Order.items[]` (дохід).

### 9.16 Налаштування — Загальні

- **Поля:** назва магазину (`Tenant.name`), API-ключ для воронки (`Tenant.apiKey`, з
  кнопкою «показати»/«перегенерувати» — перегенерація з попередженням, що стару воронку
  треба оновити).
- **Дані:** `Tenant`.

### 9.17 Налаштування — Інтеграції

- **Блоки:**
  - **Zernio** — статус підключення рекламних кабінетів, кнопка «Підключити кабінет»,
    список уже підключених з датою останньої синхронізації витрат.
  - **Нова Пошта** — поле API-ключа, статус останньої синхронізації статусів ТТН.
  - **Webhook воронки** — готовий URL + інструкція, що вставити в `funnelKey` воронки
    (аналог `TELEGRAM_CONNECTOR_ID`-патерну — секрет живе у ключах воронки).
- **Дані:** `Tenant` (зберігає токени інтеграцій).
