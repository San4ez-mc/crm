# Fineko CRM — документація API

Магазин: **{{SHOP}}**
Адреса API: **{{ORIGIN}}/api**
Згенеровано: {{DATE}}

Цей файл написано так, щоб його міг прочитати і живий розробник, і ШІ-агент (Claude, ChatGPT, Cursor тощо): достатньо передати його як контекст і сказати, що треба зробити. Усі приклади робочі, замініть лише `<API_KEY>` на ключ із CRM (Налаштування → Загальні → «API-ключ для воронки», кнопка «Показати»).

## 0. Коротко (швидкий старт)

1. Є два ключі, **їх не можна плутати**:
   - **API-ключ** (повний) — читає й змінює все в магазині. Лише для серверів: PHP/Node-бекенд, Flows, MCP. **Ніколи не вставляйте в HTML/JS сторінки.**
   - **Відкритий ключ** (`pk_…`) — вміє лише створити замовлення з лендінгу. Можна вставляти в код сторінки. Створюється кнопкою в тому ж розділі налаштувань.
2. Кожен запит — HTTPS, JSON, заголовок `Authorization: Bearer <API_KEY>`. Магазин визначається за ключем, `tenantId` передавати не треба.
3. Відповідь завжди має форму `{ "ok": true, "data": … }` або `{ "ok": false, "error": { "code", "message" } }`.
4. Створити замовлення з форми сайту — `POST /orders` (розділ 3.1) із сервера сайту або `POST /public/landing-order` (розділ 4) прямо з браузера.

Мінімальний робочий запит:

```bash
curl -X POST "{{ORIGIN}}/api/orders" \
  -H "Authorization: Bearer <API_KEY>" -H "Content-Type: application/json" \
  --data-binary @order.json
```

де `order.json`:

```json
{
  "buyer": { "phone": "+380671234567", "fullName": "Іван Петренко" },
  "items": [{ "name": "Худі оверсайз", "price": 1290, "quantity": 1,
              "properties": [{ "name": "Розмір", "value": "L" }] }],
  "shipping": { "city": "Київ", "warehouse": "Відділення №5" },
  "sourceName": "Лендінг: example.com",
  "placedBy": "Лендінг",
  "stageName": "Замовлення прийняте",
  "paymentType": "cod"
}
```

> Кирилицю в тілі запиту надсилайте з файлу (`--data-binary @файл`), а не інлайн у `-d '…'` — деякі термінали (особливо Git Bash на Windows) псують байти.

## 1. Загальні правила

| Тема | Правило |
|---|---|
| Автентифікація | `Authorization: Bearer <API_KEY>`. Без заголовка або з невірним ключем — `401`. |
| Формат | Запити й відповіді — JSON (`Content-Type: application/json`). |
| Відповідь успіху | `{ "ok": true, "data": … }`. У списків ще `meta: { total, take, skip }`. |
| Відповідь помилки | `{ "ok": false, "error": { "code", "message", "context"? } }`. |
| Коди помилок | `400` — невірні дані (`VALIDATION`), `401` — ключ, `404` — не знайдено, `409` — конфлікт, `429` — забагато запитів (лише відкритий вхід), `500` — помилка сервера. |
| Пагінація | `take` (скільки) і `skip` (скільки пропустити), у рядках: `?take=100&skip=0`. |
| Дати у фільтрах | `YYYY-MM-DD`. Кінець періоду (`to`, `ftTo`) включає всю добу. Час — київський. |
| Гроші | Гривні, число (`1290` або `1290.50`). |
| CORS | Дозволено запити з будь-якого походження, але повний ключ у браузері все одно не використовуйте. |

### Телефон — шліть в одному форматі

CRM лише прибирає зайві символи (залишає цифри й `+`), **код країни не додає**. `0671234567` і `+380671234567` будуть двома різними покупцями. Завжди шліть `+380XXXXXXXXXX`. Відкритий вхід (розділ 4) нормалізує номер сам.

### Магазини й воронка

Магазин ізольований: ключ бачить лише свої замовлення, покупців, товари. Замовлення рухається по **стадіях** воронки (`GET /pipelines`). Стадії зіставляються **за назвою**; у магазині `goverla_shop` і його копії `goverla_landing` вони такі (у нових магазинів набір коротший, актуальний список завжди дає `GET /pipelines`):

1. Презентація товару
2. Написав параметри
3. Написав параметри та колір
4. Очікуємо дані та оплату
5. Замовлення прийняте
6. Замовлення оформлене в постачальника
7. Відправлено
8. Посилка зберігається на пошті
9. Не забрав на пошті
10. Клієнт забрав на пошті
11. Повернення/обмін

Стадії «Не відписали протягом доби» і «Скасовано» прибрано: скасоване замовлення тепер просто **видаляється** (`DELETE /orders/:id`), воно зникає зі списку й усіх звітів, але лишається в базі з платежами та ТТН.

Стадії 1–4 — це розмова з ботом. Замовлення із сайту має одразу йти в **«Замовлення прийняте»** (передайте `"stageName": "Замовлення прийняте"`). Без стадії замовлення потрапить у першу — «Презентація товару».

Далі стадії рухає сама CRM: ТТН постачальника → лишається «оформлене в постачальника»; щогодини CRM питає Нову пошту і переводить у «Відправлено» → «Посилка зберігається на пошті» → «Клієнт забрав» / «Не забрав». Вручну ці стадії ставити не потрібно.

## 2. Модель замовлення

Основні поля `Order` у відповідях:

| Поле | Значення |
|---|---|
| `id` | Ідентифікатор (UUID). |
| `buyer` | Покупець: `{ id, phone, fullName, igUsername }`. |
| `stage` | Поточна стадія: `{ id, name, pipeline }`. |
| `items[]` | Позиції: `{ name, price, quantity, properties:[{name,value}], isUpsell, productId?, supplier? }`. |
| `shipping` | `{ city, warehouse, fullName?, phone? }`. |
| `sourceName` | **Джерело** — вільний текст. Показується в колонці «Джерело» й у картці, якщо замовлення не з реклами. |
| `managerComment` | Коментар для менеджера. |
| `paymentType`, `prepaymentAmount` | Спосіб оплати і передоплата (див. 3.1). |
| `ttn[]`, `ttnStatus`, `ttnEta` | Номери ТТН і статус Нової пошти. |
| `placedAt`, `placedBy` | Коли й ким оформлено. Від `placedAt` рахуються звіти. |
| `isRefused` | Прапорець відмови (ставить CRM за статусом пошти). |
| `firstTouchAd`, `lastTouchAd` | Реклама, з якої прийшов клієнт (якщо відома). |
| `createdAt` | Коли запис створено. |

## 3. Запити (з повним API-ключем)

Усі шляхи нижче — відносно `{{ORIGIN}}/api`.

### 3.1 Замовлення

#### `POST /orders` — створити замовлення

Тіло:

| Поле | Обовʼязкове | Опис |
|---|---|---|
| `items[]` | **так** | Хоча б одна позиція: `name`, `price`, `quantity` (за замовчуванням 1), `properties` (колір/розмір), `productId`/`offerId` (якщо знаєте з каталогу), `isUpsell`. |
| `buyer` | ні* | `{ phone, fullName, igUsername }` — покупця буде знайдено за телефоном або створено. Або `buyerId`. *Без покупця запис вважається «карткою розмови», а не оформленим замовленням — у звітах його не буде. Для замовлень із сайту завжди передавайте `buyer.phone`. |
| `shipping` | ні | `{ city, warehouse }`. Запамʼятовується на покупцеві для наступних замовлень. |
| `sourceName` | ні | Джерело, напр. `"Лендінг: example.com"`. |
| `managerComment` | ні | Коментар клієнта/UTM для менеджера. |
| `stageId` або `stageName` | ні | Стадія: id або назва (`"Замовлення прийняте"`). Не вказано — перша стадія воронки. |
| `paymentType` | ні | `cod` (накладений платіж, передоплата 0), `partial` (часткова; сума в `prepaymentAmount`, за замовчуванням — з налаштувань магазину), `full` (повна). |
| `prepaymentAmount` | ні | Лише для `partial`, не більша за суму. |
| `placedBy` | ні | Хто оформив (рядок, до 80 символів), напр. `"Лендінг"`. |
| `placedAt` | ні | Дата оформлення ISO; за замовчуванням «зараз». |
| `ttn` | ні | Номери ТТН (масив або рядок). |

Відповідь `201`: `{ "ok": true, "data": { …замовлення… } }`. Якщо передано `funnelSessionId` і така картка вже є — оновлюється вона, а не створюється друге замовлення.

**Дублі.** `POST /orders` сам дублі не склеює. Подвійне натискання кнопки створить два замовлення — вимикайте кнопку після кліку або перевіряйте на своєму боці.

#### `GET /orders` — список

Параметри: `take`, `skip`, `q` (телефон, ТТН, імʼя, Instagram-нік або посилання), `stageId`, `ftFrom`/`ftTo` (за датою **оформлення**), `from`/`to` (за датою створення), `productId`, `adId`, `noAd=1` (оформлені без реклами).

#### Решта

| Запит | Що робить |
|---|---|
| `GET /orders/:id` | Одне замовлення з позиціями, оплатами, повʼязаною рекламою. |
| `PATCH /orders/:id` | Змінити лише передані поля: `stageId`, `shipping`, `managerComment`, `ttn`, `sourceName`, `paymentType`, `prepaymentAmount`, `placedAt`, `placedBy`, `isRefused`, `contactName`, `contactIg`, `buyer`. Нова ТТН автоматично переводить замовлення далі за воронкою. |
| `PUT /orders/:id/items` | Замінити всі позиції: `{ "items": [ … ] }`. |
| `DELETE /orders/:id` | Видалити замовлення (навіть оформлене): зникає зі списку й усіх звітів, у базі лишається, відновити можна. `POST /orders/:id/cancel` робить те саме. |
| `POST /orders/:id/restore` | Відновити видалене замовлення. |
| `GET /orders/summary` | Кількість і сума по статусах (ті самі фільтри, що в списку). |
| `GET /orders/export.xlsx` | Файл Excel за тими самими фільтрами (потрібен лише заголовок Authorization). |
| `GET /orders/lookup-client?ig=…&phone=…&funnelSessionId=…` | Останнє оформлене замовлення клієнта; `data: null`, якщо немає. |
| `POST /orders/:id/ttn-refresh` | Одразу спитати Нову пошту про статус ТТН. |

### 3.2 Покупці

| Запит | Що робить |
|---|---|
| `GET /buyers?q=…&take=50&skip=0` | Пошук за імʼям, телефоном, Instagram-ніком. |
| `POST /buyers/find-or-create` | `{ phone, fullName?, igUsername? }` → знайти за телефоном або створити. |
| `GET /buyers/lookup?phone=…&igUsername=…` | Знайти без створення; `data: null`, якщо немає. |
| `GET /buyers/:id` | Покупець з усіма замовленнями. |
| `PATCH /buyers/:id` | Змінити покупця (імʼя, виміри, збережена доставка). |

### 3.3 Оплати й повернення

| Запит | Що робить |
|---|---|
| `GET /payments?orderId=…` | Оплати магазину або одного замовлення. |
| `POST /payments` | `{ orderId, amount, method?, status? }` — записати оплату (`status` за замовчуванням `success`). |
| `GET /returns` | Повернення й обміни. |
| `POST /returns` | `{ orderId, type: "return" \| "exchange", reason?, ttn?, exchangeFor? }`. |
| `PATCH /returns/:id` | Змінити статус повернення. |

### 3.4 Каталог, воронка, база знань

| Запит | Що робить |
|---|---|
| `GET /products?q=…&sku=…&take=50` | Товари (ціна, кольори/розміри, фото). |
| `GET /products/:id` | Один товар. |
| `GET /pipelines` | Воронки зі стадіями (звідси беруть `stageId`). |
| `POST /funnel-events` | Подія воронки бота `{ sessionId, stageName, … }` — створює/рухає картку розмови. Для сайтів не потрібна. |
| `GET /funnel-events/summary` | Конверсія по етапах. |
| `GET /knowledge/search?q=…` | Пошук у базі знань магазину. |

## 4. Відкритий вхід для лендінгу (без повного ключа)

Для сторінок, що шлють замовлення прямо з браузера, без власного серверного коду.

`POST {{ORIGIN}}/api/public/landing-order`

Ключ — відкритий (`pk_…`): у тілі як `key` або заголовком `X-Public-Key`. Він вміє **лише створити замовлення**.

| Поле | Опис |
|---|---|
| `key` | Відкритий ключ магазину. **Обовʼязкове.** |
| `name` | Імʼя клієнта. **Обовʼязкове.** |
| `phone` | Телефон у будь-якому форматі (`067 123-45-67`, `+380…`) — CRM приведе до `+380…`. **Обовʼязкове.** |
| `items[]` | **Обовʼязкове**, до 20 позицій: `{ sku?, name, price, quantity?, properties? }`. Якщо `sku` є в каталозі магазину — ціну й назву CRM бере з каталогу (захист від підміни в браузері). |
| `city`, `warehouse` | Доставка. |
| `comment` | Коментар клієнта. |
| `source` | Адреса/назва сторінки → у «Джерело» запишеться `Лендінг: <source>`. |
| `utm` | Обʼєкт UTM-міток → потрапляє в коментар менеджеру. |
| `paymentType` | `cod` (за замовчуванням) / `partial` / `full`. |
| `instagram` | Нік або посилання на Instagram (необовʼязково). |
| `website` | **Пастка для ботів.** Додайте приховане поле з таким імʼям, людина його не заповнює. Заповнене — замовлення мовчки відкидається. |

Що робить сервер автоматично: ставить стадію «Замовлення прийняте», `placedBy = "Лендінг"`, склеює повторне натискання (той самий телефон і склад за 10 хвилин → повертає вже створене замовлення з `duplicate: true`), обмежує 8 запитів за 10 хвилин з однієї адреси (далі `429`).

Відповідь: `201 { "ok": true, "data": { "orderId": "…" } }`.

Приклад для HTML-сторінки:

```html
<script>
function sendFinekoOrder(data) {
  var utm = {};
  new URLSearchParams(location.search).forEach(function (v, k) { if (/^utm_|^fbclid$/.test(k)) utm[k] = v; });
  return fetch('{{ORIGIN}}/api/public/landing-order', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(Object.assign({ key: 'pk_ВАШ_ВІДКРИТИЙ_КЛЮЧ', source: location.hostname + location.pathname, utm: utm }, data))
  }).then(function (r) { return r.json().catch(function () { return {}; }); })
    .then(function (j) { if (!j.ok) throw new Error((j.error && j.error.message) || 'Не вдалося відправити'); return j.data; });
}
</script>
```

## 5. Приклади

### PHP (з сервера сайту — рекомендовано)

Ключ лежить у PHP, у браузер не потрапляє.

```php
<?php
$order = [
  'buyer' => ['phone' => $_POST['phone'], 'fullName' => $_POST['name']],
  'items' => [['name' => 'Худі оверсайз', 'price' => 1290, 'quantity' => 1]],
  'shipping' => ['city' => $_POST['city'] ?? '', 'warehouse' => $_POST['warehouse'] ?? ''],
  'sourceName' => 'Лендінг: ' . $_SERVER['HTTP_HOST'],
  'placedBy' => 'Лендінг',
  'stageName' => 'Замовлення прийняте',
  'paymentType' => 'cod',
  'managerComment' => $_POST['comment'] ?? '',
];
$ch = curl_init('{{ORIGIN}}/api/orders');
curl_setopt_array($ch, [
  CURLOPT_POST => true, CURLOPT_RETURNTRANSFER => true, CURLOPT_TIMEOUT => 15,
  CURLOPT_HTTPHEADER => ['Authorization: Bearer ' . getenv('CRM_API_KEY'), 'Content-Type: application/json'],
  CURLOPT_POSTFIELDS => json_encode($order, JSON_UNESCAPED_UNICODE),
]);
$res = json_decode(curl_exec($ch), true);
if (empty($res['ok'])) {
  error_log('CRM: ' . ($res['error']['message'] ?? 'немає відповіді'));
  // покажіть клієнту «спробуйте ще раз», не втрачайте замовлення: збережіть його у файл/пошту
}
```

Поради: ключ тримайте в змінній середовища або конфігу поза веб-коренем; таймаут 15 с; якщо CRM не відповіла — збережіть замовлення локально й повторіть, щоб не втратити клієнта.

### Node.js (сервер)

```js
const res = await fetch('{{ORIGIN}}/api/orders?take=20', {
  headers: { Authorization: `Bearer ${process.env.CRM_API_KEY}` },
});
const { ok, data, meta, error } = await res.json();
if (!ok) throw new Error(error.message);
```

### curl — список останніх замовлень

```bash
curl -H "Authorization: Bearer <API_KEY>" "{{ORIGIN}}/api/orders?take=20"
```

## 6. Інструкція для ШІ-агента

Якщо ви — ШІ-агент і вам передали цей файл, дотримуйтесь:

1. Використовуйте **лише** описані тут запити й поля. Не вигадуйте нових шляхів і параметрів; якщо чогось бракує — скажіть про це людині.
2. **Ніколи не вставляйте повний API-ключ** у HTML, JavaScript сторінки, публічний репозиторій, логи чи відповідь людині. У клієнтському (браузерному) коді дозволений лише відкритий ключ `pk_…` і лише для `POST /public/landing-order`.
3. Не видаляйте і не змінюйте існуючі замовлення без прямого прохання людини. `DELETE /orders/:id` — лише для тестових записів, які ви самі створили.
4. Перед масовими змінами (цикл по багатьох замовленнях) покажіть людині, що саме зміниться, і дочекайтесь підтвердження.
5. Телефон завжди у форматі `+380XXXXXXXXXX`. Замовлення з сайту — завжди з `buyer.phone`, `sourceName`, `placedBy`, `stageName: "Замовлення прийняте"`.
6. Перевіряйте `ok` у кожній відповіді; при `ok: false` читайте `error.message` і не повторюйте той самий запит у нескінченному циклі. Для `429` — почекайте кілька хвилин.
7. Захист від дублів на боці клієнта: блокуйте кнопку після натискання; для повторної відправки не створюйте нове замовлення, поки не переконались, що перше не дійшло.
8. Стадії воронки не змінюйте вручну без потреби, — CRM сама рухає їх за ТТН і Новою поштою. Скасоване замовлення видаляйте (`DELETE /orders/:id`).
9. Для тесту створюйте замовлення з очевидною позначкою («ТЕСТ») і прибирайте їх після перевірки.

## 7. Чекліст підключення лендінгу

- [ ] Магазин для лендінгу створено в CRM (є свій API-ключ або відкритий ключ).
- [ ] Менеджерам дано доступ до цього магазину в SSO-панелі.
- [ ] Форма шле `name`, `phone`, товар(и), доставку; номер у форматі `+380…`.
- [ ] У замовленні виставлено джерело (`sourceName` / `source`) — щоб бачити, з якої сторінки прийшло.
- [ ] Кнопка «Замовити» блокується після натискання.
- [ ] Протестовано: тестове замовлення зʼявилось на дошці в «Замовлення прийняте» з джерелом «Лендінг: …», тест видалено.
- [ ] Ключ не потрапив у публічний код сторінки.
